# Handover — 2026-08-27

1.19.0 is tagged and pushed; whether it is published depends on when you read this. Two
things in it matter beyond the feature list, and the first has consequences outside this
repository.

---

## `threshold` never did what it said, and now does

`filter_frame_ffmpeg` built `[0:v][1][2][diff]threshold`. FFmpeg's `threshold` filter emits
its `min` where its **first** input is below the second, and the first input there was the
original video, not the difference. So the parameter masked motion where the *picture* was
dark and passed every difference through untouched where the picture was bright: a darkness
mask, documented in `_motionvideo.py` as "discards small pixel differences, which removes
sensor noise". It removed none.

Verified on a synthetic clip rather than by reading the standard — a 3-level change survives
at brightness 200 and is zeroed at brightness 5.

**The two implementations disagreed.** The numpy `filter_frame` always thresholded the
difference, so `threshold=0.05` meant one quantity in `mg_motion`, `_tracks` and `_utils`,
and another in `_impacts` and `_directograms`. `'Binary'` was correct all along.

**It changes every quantity-of-motion number this package has produced.** Measured on six
100-minute recordings: the median falls by 67 to 90 per cent, and the
99th-percentile-to-median ratio roughly triples (one recording 3.3 → 19.3). What looked like
recordings with compressed dynamic range were recordings whose noise floor sat highest
relative to their signal.

**Nothing in the suite failed when it was fixed**, which is why it lasted: no test could tell
the two behaviours apart. The new ones use input whose answer is known by construction.

Left for you: whether the version number is honest. This went out as a fix in 1.19.0 on the
argument that the documented contract never changed, only the implementation, and that the
2.0 plan reserves that number for API hygiene. It is defensible and it is not the only
defensible answer.

## Motion vectors, and what they are for

An inter-frame codec has already searched for every macroblock's displacement. Reading its
answer costs about what reading the file costs — 2.2 s to decode 6000 frames of 1080p, 2.7 s
to decode them with the vectors — against 27 minutes to difference the same session's pixels.

New: `motionvectordata`, `motionvectorhistory`, `motionvectorgrams`, `motionvectorwaterfall`,
`motionvectoroverview` and `motionscape`. The overview does every view in **one decode**,
which is the whole point for archive triage: four views that each open the file cost four
times what they need to.

`motionscape` is Sapp's keyscape construction over quantity of motion and takes any
per-frame track, so it scapes a frame-differenced series just as readily.

**What the vectors are and are not.** They correlate with frame differencing at r ≈ 0.83
median *within* a recording. They do **not** transfer between recordings: the conversion
factor across six sessions spanned 12.5×, and ranking the sessions by median motion agreed
with frame differencing at only Spearman 0.66. Interestingly the instability is mostly frame
differencing's — its median spans 73× across these six against the vectors' 5.4×, because
thresholding makes it violently nonlinear in contrast. Which of the two is the better
cross-dataset measure is **not settled**, and settling it needs ground truth neither has.

## Three faults of mine, all the same shape

Each was invisible to the test suite and fatal on real material, and the suite is short-clip
by nature, so none of them could have been caught by testing harder on clips.

- **`motion_vector_grid` stacked every frame.** 20 GB per array on a 100-minute 1080p
  recording, three of them. Now a generator. The test measures how peak allocation grows
  with length rather than whether a clip succeeds — the only form that catches this class.
- **A Python loop per motion vector.** 8,160 macroblocks a frame, 2.5 billion iterations over
  a session. Now a `bincount`, exact because every H.264 partition lies inside one
  macroblock (checked: 0 of 12,130 vectors crossed a cell boundary).
- **`motionscape` read `self.qom_track`, an attribute I invented.** The branch could never
  fire, so `source='framediff'` was decorative and would have silently scaped the vectors.
  mypy over the package caught it; mypy over the one file did not.

**Reproducing the lint job needs a dependency-free environment.** In the dev venv mypy
reports 95 errors where CI reports 9, and pinning to CI's 2.3.1 does not close the gap: the
lint job installs only ruff and mypy, so third-party imports resolve differently. A venv with
just those two pinned tools is the only local command that predicts that job.

## Also worth knowing

**Frame-threaded decoding drops motion vectors nondeterministically** — three identical runs
gave 28,702, 29,649 and 29,975 on one clip. On real 1080p the loss is 0.0009 per cent and
threading is 4.5× faster, so it stays the default with `deterministic=True` available.

**FFmpeg exports vectors for H.264 and MPEG-4 Part 2 only.** HEVC and VP9 decode and return
zero. `motionvectordata` warns, because zeros otherwise read as stillness.

**MediaPipe 1.0 removed `mp.solutions`.** `_posetools` already branches on
`hasattr(mp, "solutions")`, so the Tasks path carries it; the Solutions branch is now
unreachable on any installable wheel and its TODO can be actioned.
