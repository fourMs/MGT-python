### Two release-path faults, both now written down

**The publish workflow refused, correctly, and `RELEASING.md` did not say it would.** The workflow
opens with a job called *Refuse to publish from a commit CI has not passed*, and `in_progress` counts
as not passed. Pushing the commit and creating the Release in the same breath therefore fails: the
release exists, the run goes red at its first job, nothing is built and nothing reaches PyPI. That
happened to 1.14.0. The order is push, **wait for CI**, then `gh release create`; the repair is
`gh run rerun <id>`. `RELEASING.md` carries this now.

**The release guard had a bug in itself.** `test_every_changelog_version_has_a_tag` looked only for
`v`-prefixed tags. This project stopped using that prefix on 2026-08-16, so the check passed for
exactly as long as the newest release was the one it skips: 1.13.0 was tagged bare, and the test went
red the moment 1.14.0 sat above it, blaming a correctly tagged release. It accepts both conventions
now, verified by reverting to the v-only rule and watching it fail.

**And the changelog's compare links were dead for two releases.** `[Unreleased]` still compared from
`v1.12.1`, and 1.13.0 and 1.14.0 had no link reference at all. That test checks *tags*, not *links*,
so it could not have caught this.

### The Zenodo DOIs — the one item with reach beyond this repo

**The GitHub integration works and has since 2026-08-16**, contrary to what the Sound Spaces handover
said. It has archived every release since unattended. But it never adopted the concepts deposited by
hand on 2026-08-15, so **every toolbox has two lineages**: a frozen record holding one version, and a
live one holding everything since.

Sound Spaces' twenty reports had cited the frozen column for nine days; that is corrected. Three
musicalgestures records also stated a `v`-prefixed version from the 2026-08-22 tag backfill, and are

**Zenodo cannot merge two concepts, so the frozen records stay.** micromotion's README explains its
own pair and points at the live one. **The other three repositories do not, and whether they should
is yours.** Anyone who cited a frozen DOI is citing something real that will never advance.

`deposit/_curation/toolbox_zenodo_check.py` in the Still Standing tree checks both faults and exits
non-zero, so a release can be gated on it.

## One measured thing worth carrying into #373

From the pyeyesweb assessment, because it changes how smoothness should be computed from pose:
over 15 repeats per noise level, **jerk RMS rises 8.6× at 10 per cent tracker noise while SPARC does
not move at all** — and real roughness, three submovements with no noise, also reads 9.0× on jerk.
So jerk cannot distinguish tracker noise from tripling the submovements. A smoothness claim about a
performer, computed from MediaPipe landmarks with jerk, is largely a claim about MediaPipe.
